03 · Metodologia & Engenharia de Qualidade

Como eu testo na prática

Navegue pelas abas abaixo (clique ou use as setas do teclado ← →) para inspecionar meus padrões reais de arquitetura, reporte de defeitos, BDD e regressão contínua.

A IA acelera a geração, mas a engenharia e a revisão são 100% humanas

Utilizo LLMs e Agentes de IA guiados por regras de sistema (@RafaQA.rules) para expandir cobertura de cenários negativos, refatorar Page Objects e revisar PRs de testes, sustentado por 3 pilares inegociáveis:

Pilar 01

Arquitetura em camadas sem código duplicado

A IA nunca gera scripts monolíticos. Todo código assistido respeita a árvore de Page Objects, Keywords ou Steps existentes no projeto, reaproveitando helpers de autenticação, esperas explícitas e fixtures.

Pilar 02

Validação de falha real (Teste que nunca falha não protege)

Todo teste automatizado passa por mutação ou inversão da asserção antes do merge para comprovar que ele realmente quebra quando a regra de negócio ou contrato da API REST é violado.

Pilar 03

Segurança & Zero dados reais no prompt

Conformidade rigorosa com LGPD e políticas corporativas: tokens, endpoints privados, CPFs ou payloads de clientes financeiros/Salesforce são anonimizados e substituídos por contratos sintéticos.

Resiliência contra Flakiness & Separação em Camadas

A principal causa de falsos negativos em E2E é acoplar o teste à estrutura visual do DOM ou misturar locators com regras de negócio.

✕ Frágil (Acoplado ao layout / classes dinâmicas) 
// Quebra em qualquer ajuste de CSS ou div
const btn = page.locator(
  'xpath=/html/body/div[2]/div/main/form/div[4]/button[1]'
);
await page.locator('.css-1x9f8a-btnPrimary').click();
await page.waitForTimeout(5000); // Sleep fixo = lentidão + flakiness
✓ Estável (Atributo funcional & Web-First Assertions) 
// Resiliente, semântico e auto-waiting nativo
const submitOrderBtn = page.getByTestId('checkout-submit-btn');
// ou acessível por role WCAG:
// page.getByRole('button', { name: 'Finalizar Pedido' })
await submitOrderBtn.click();
await expect(page.getByTestId('order-status')).toHaveText('Aprovado');
Camada 1 Testes / Specs Orquestra o cenário e valida asserções de negócio
→
Camada 2 Keywords / Steps Ações reutilizáveis de domínio (ex: fecharPedidoPix)
→
Camada 3 Page Objects Encapsula locators estáveis (data-testid / roles)
→

BUG-4092 · Finanças / Checkout E-commerce

[API/Web] Cobrança duplicada ao reenviar confirmação de pagamento via Pix com latência acima de 3s

Severidade: Alta (Crítica) Prioridade: P1 (Imediata)
Ambiente: Staging (v2.18.4) · Chrome 130 / AWS Lambda Gateway
Módulo: Checkout & Integração CRM Salesforce
Descoberto via: Automação E2E Playwright + Teste de Stress JMeter

Passos para Reproduzir

  1. Autenticar com usuário válido no ambiente Staging e adicionar um item ao carrinho.
  2. Avançar para o pagamento, selecionar a modalidade Pix e interceptar/simular latência de 3.500ms na rota POST /api/v1/payments/pix/confirm.
  3. Acionar o botão Confirmar Pagamento duas vezes consecutivas dentro da janela de carregamento.
  4. Consultar os registros gerados no banco PostgreSQL e a oportunidade sincronizada no CRM Salesforce.
✓ Resultado Esperado

O botão deve entrar em estado disabled/loading no primeiro clique e a API deve validar a chave de idempotência (Idempotency-Key), processando apenas 1 transação.

✕ Resultado Obtido

O front-end permite múltiplos disparos e o endpoint retorna dois HTTP 201 Created com transaction_id distintos, gerando cobrança duplicada no extrato e 2 registros no Salesforce.

Evidências Anexadas: trace-playwright-bug4092.zip · har-network-duplicate-post.har · cloudwatch-lambda-request-id-99a8b.log

Funcionalidade: Transferência via Pix com validação de limite diário
  Como correntista autenticado na plataforma financeira
  Quero realizar transferências instantâneas via Pix
  Para liquidar pagamentos respeitando meu limite de segurança configurado

  Esquema do Cenário: Processamento de Pix dentro e fora do limite diário
    Dado que o correntista possui saldo disponível de "R$ 5.000,00"
    E seu limite diário disponível para Pix é de "R$ 2.000,00"
    Quando solicita uma transferência Pix no valor de "<valor_pix>" para chave válida
    Então a API deve responder com status HTTP <status_http>
    E a interface deve exibir a mensagem "<mensagem_esperada>"

    Exemplos:
      | cenario          | valor_pix   | status_http | mensagem_esperada                              |
      | Caminho Feliz    | R$ 1.500,00 | 201         | Transferência Pix realizada com sucesso        |
      | Limite Exato     | R$ 2.000,00 | 201         | Transferência Pix realizada com sucesso        |
      | Acima do Limite  | R$ 2.000,01 | 422         | Valor excede o limite diário disponível (R$ 2k)|
