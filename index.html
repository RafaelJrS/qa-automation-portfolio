COMO EU REVISO O QUE A IA ENTREGA
01 Arquitetura em camadas sem duplicação.

Código gerado só entra no repositório se reutilizar Page Objects, Keywords, Steps e DataPools existentes.

02 Validação de falha real.

Teste que nunca ficou vermelho não prova nada. Inverto a asserção ou quebro a regra para garantir que o teste detecta regressões.

03 Zero dados reais no prompt.

Tokens, endpoints internos, CPFs e payloads de clientes financeiros ou Salesforce ficam 100% fora da conversa com o modelo.

02 · ARQUITETURA & SELETORES

Seletores resilientes e separação estrita em 4 camadas.

✕ Seletor Frágil (XPath absoluto / Classe dinâmica / Sleep fixo) 
// Quebra com qualquer mudança visual no DOM
const btn = page.locator('xpath=/html/body/div[2]/main/form/div[4]/button[1]');
await page.locator('.css-1x9f8a-btnPrimary').click();
await page.waitForTimeout(5000); // Flakiness e lentidão na pipeline CI
✓ Seletor Estável (data-testid / Role acessível + Auto-Wait) 
// Resiliente a mudanças de layout e aderente a acessibilidade
const finishBtn = page.getByTestId('checkout-finish-btn');
// ou: page.getByRole('button', { name: 'Confirmar Pedido' })
await finishBtn.click();
await expect(page.getByTestId('order-status')).toHaveText('Pedido Confirmado');

→
Camada 02 Keywords / Steps Fluxos reutilizáveis de domínio (ex: realizarCheckoutPix)
→
Camada 03 Page Objects Encapsula locators estáveis e interações de página
→
Camada 04 DataPool / Fixtures Massas sintéticas, contratos JSON e variáveis de ambiente
03 · REPORTE DE DEFEITOS ESTRUTURADO

Evidência clara para resolução rápida sem retrabalho.

BUG-4092 · Checkout Financeiro & CRM Salesforce

[API/Web] Cobrança duplicada ao confirmar pagamento Pix sob latência de rede (>3s)

Severidade: Crítica (S1) Prioridade: Alta (P1)
Ambiente: Staging v2.18.4 · Chrome 130 / AWS API Gateway
Módulo: Pagamentos Instantâneos & Sync Salesforce
Origem: Automação E2E Playwright + Teste de Stress JMeter

Passos para Reproduzir

  1. Autenticar na plataforma Staging com conta ativa e adicionar produto ao carrinho.
  2. Selecionar pagamento via Pix e simular throttling de rede (3.500ms) no endpoint POST /api/v1/payments/pix/confirm.
  3. Acionar o botão Finalizar Pagamento duas vezes seguidas antes do retorno da requisição.
  4. Verificar tabela de transações no PostgreSQL e oportunidades criadas no CRM Salesforce.
✓ Resultado Esperado

O botão deve ficar desabilitado (disabled) após o 1º clique e o backend deve validar Idempotency-Key, registrando apenas 1 débito.

✕ Resultado Obtido

Duas requisições retornam HTTP 201 Created com IDs distintos, debitando o saldo em duplicidade e abrindo 2 registros no Salesforce.

Evidências: playwright-trace-4092.zip · network-duplicate-pix.har · aws-lambda-cloudwatch.log

Funcionalidade: Limite diário de transferência Pix
  Esquema do Cenário: Validar transferência dentro e acima do limite
    Dado que o cliente possui saldo de "R$ 5.000,00" e limite Pix de "R$ 2.000,00"
    Quando envia um Pix de "<valor>" para uma chave válida
    Então a API retorna HTTP <status> e a mensagem "<retorno>"

    Exemplos:
      | cenario         | valor       | status | retorno                                |
      | Caminho Feliz   | R$ 1.500,00 | 201    | Transferência Pix realizada com sucesso|
      | Fronteira Exata | R$ 2.000,00 | 201    | Transferência Pix realizada com sucesso|
      | Fronteira +0,01 | R$ 2.000,01 | 422    | Valor excede o limite diário disponível|
